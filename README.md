# multicast-discovery

Приложение на Go, которое обнаруживает в локальной сети другие запущенные
копии самого себя с помощью обмена multicast UDP-сообщениями. Как только
список "живых" копий меняется (кто-то появился или кто-то пропал), в
консоль выводится актуальный список их IP-адресов.

Протокол (IPv4 или IPv6) определяется автоматически по виду адреса
multicast-группы, который вы передаёте параметром — никаких отдельных
флагов "включить IPv6" не нужно.

Этот README написан подробно и построчно специально для человека, который
только начинает работать с Go: каждый файл разобран построчно, а термины
вроде "multicast" и "горутина" объяснены по ходу дела.

## 1. Что такое multicast и как приложение им пользуется

Обычный UDP- или TCP-пакет отправляется **одному конкретному** адресату
(unicast — "один к одному"). **Multicast** ("один ко многим") — это
специальный режим, в котором пакет отправляется не на IP-адрес конкретного
компьютера, а на адрес **группы**. Любой компьютер в локальной сети,
который "подписался" на эту группу (говорят "присоединился к группе",
join), получит этот пакет, даже если отправитель вообще не знает, кто
именно в сети сейчас слушает.

- Для IPv4 multicast-адреса — это диапазон `224.0.0.0`–`239.255.255.255`
  (например, `224.1.1.1`).
- Для IPv6 multicast-адреса начинаются с `ff` (например, `ff02::1234`).

Идея приложения простая:

1. Каждая запущенная копия приложения **присоединяется** к указанной
   multicast-группе и **слушает** её — это делает файл `listener.go`.
2. Каждая копия **раз в несколько секунд** отправляет в эту же группу
   короткое сообщение "я жив, вот мой идентификатор" — это делает файл
   `sender.go`.
3. Когда копия получает такое сообщение от кого-то другого, она
   запоминает его IP-адрес и время получения — это делает файл
   `tracker.go`.
4. Если от какой-то копии долго (дольше `-timeout`) не было сообщений —
   она считается пропавшей и удаляется из списка.
5. При любом изменении списка (кто-то появился или пропал) список
   IP-адресов заново печатается в консоль — это делает файл `printer.go`.

Все копии в сети выполняют одновременно и роль отправителя, и роль
слушателя — то есть все они равноправны, нет отдельного "сервера" и
"клиентов".

## 2. Структура проекта

Логика намеренно разложена по отдельным файлам с чёткой ответственностью
каждого — вместо одной большой функции, которая делает всё сразу.
Исходники сознательно без комментариев — расширенные пояснения к каждому
файлу вынесены сюда, в README.

| Файл          | За что отвечает                                                                 |
|---------------|----------------------------------------------------------------------------------|
| `main.go`     | Точка входа: связывает все части вместе, обрабатывает сигнал остановки          |
| `flags.go`    | Разбор и проверка параметров командной строки (`-group`, `-port` и т.д.)         |
| `idgen.go`    | Генерация уникального идентификатора текущего процесса                          |
| `netutil.go`  | Вспомогательные сетевые функции: выбор IPv4/IPv6 и выбор сетевого интерфейса     |
| `sender.go`   | Периодическая отправка анонсов "я жив" в multicast-группу, закрепление исходящего интерфейса |
| `listener.go` | Приём сообщений от других копий из multicast-группы                             |
| `tracker.go`  | Потокобезопасное хранилище списка живых копий с их временем последнего анонса   |
| `printer.go`  | Вывод текущего списка живых копий в консоль                                     |
| `go.mod`      | Файл модуля Go; единственная внешняя зависимость — `golang.org/x/net`           |

Никаких платформенных файлов (`_darwin.go`, `_windows.go` и т.п.) в
проекте больше нет: закрепление исходящего multicast-интерфейса теперь
делается через официальный пакет `golang.org/x/net/ipv4` /
`golang.org/x/net/ipv6` (метод `PacketConn.SetMulticastInterface`) —
одним и тем же кодом для любой ОС, которую поддерживает сам Go (macOS,
Linux, Windows), без единого вызова `syscall` напрямую. Раньше это было
сделано через ручные `syscall.SetsockoptInt`/`SetsockoptInet4Addr` в
отдельном файле под каждую платформу — рабочий, но откровенно
низкоуровневый вариант. `golang.org/x/net` — это официальный пакет из
экосистемы Go (репозиторий `golang.org/x/...`, поддерживается той же
командой, что и сам язык), а не сторонняя библиотека с улицы.

## 3. Сборка и запуск

Требуется установленный Go (версия 1.21 или новее; в этом проекте
использовался Go 1.22). Проект использует одну внешнюю зависимость —
`golang.org/x/net` — поэтому перед первой сборкой (один раз, при наличии
интернета) нужно скачать её:

```bash
go mod tidy
```

Эта команда скачает `golang.org/x/net` (и её собственную небольшую
зависимость `golang.org/x/sys`) и создаст файл `go.sum` с контрольными
суммами. Повторно выполнять её не нужно, если только вы не меняете
зависимости.

### Сборка

Из корня проекта (папка, где лежит `go.mod`):

```bash
go build -o mcdisc .
```

Эта команда скомпилирует все `.go` файлы пакета `main` в один исполняемый
файл `mcdisc`.

### Запуск: пример на IPv4

Откройте **два разных терминала** (в идеале — на двух разных компьютерах в
одной локальной сети; для проверки сойдёт и один компьютер, запущенный
дважды) и в каждом выполните:

```bash
./mcdisc -group 224.1.1.1 -port 9999
```

Через секунду-две в каждом терминале должно появиться сообщение об
обнаружении второй копии со списком её IP-адреса. Если остановить один из
процессов (Ctrl+C или `kill`), через `-timeout` (по умолчанию 6 секунд)
второй процесс напечатает, что копия исчезла.

### Запуск: пример на IPv6

```bash
./mcdisc -group ff02::1234 -port 9999
```

Всё, что нужно сделать для переключения на IPv6, — это передать IPv6-адрес
в `-group`. Приложение само определит протокол по адресу (см. `flags.go`,
функция `parseFlags`, и подробности в разделе 6).

Для IPv6 link-local адресов (`ff02::/16`) часто требуется явно указать
сетевой интерфейс, если их на машине несколько:

```bash
./mcdisc -group ff02::1234 -port 9999 -iface en0
```

(Имя интерфейса на macOS можно узнать командой `ifconfig` — обычно это
`en0` для Wi-Fi.)

## 4. Параметры командной строки

| Флаг         | Обязательный | По умолчанию | Назначение                                                                 |
|--------------|:------------:|:------------:|------------------------------------------------------------------------------|
| `-group`     | да           | —            | Multicast-адрес группы. IPv4 (`224.х.х.х`) или IPv6 (`ffхх::...`)            |
| `-port`      | нет          | `9999`       | UDP-порт, на котором происходит обмен                                        |
| `-iface`     | нет          | авто         | Имя сетевого интерфейса (важно для IPv6, если интерфейсов несколько)         |
| `-interval`  | нет          | `2s`         | Как часто рассылать анонс "я жив"                                            |
| `-timeout`   | нет          | `6s`         | Через сколько без анонсов считать копию пропавшей (должен быть > `-interval`)|

Посмотреть эту же справку можно командой `./mcdisc -h`.

## 5. Формат сообщений (протокол)

Формат сообщения максимально простой: это **не JSON** и не какой-то
бинарный формат, а просто набор байт — уникальный идентификатор процесса
(instance ID), сгенерированный при старте (см. `idgen.go`). Например,
строка вида `7b6d3d8363f4c0c4`.

Зачем нужен идентификатор, а не просто "получил пакет — значит, кто-то
жив":

- Одна и та же машина (один и тот же IP-адрес) может одновременно
  запускать несколько копий приложения (например, вы тестируете локально,
  открыв два терминала). Идентификатор позволяет считать их **разными**
  живыми копиями, а не одной.
- Операционные системы по умолчанию доставляют multicast-пакет обратно
  тому же сокету, который его отправил ("multicast loopback"). Без
  идентификатора приложение приняло бы собственное же сообщение за
  сообщение от "другой копии". Зная свой собственный ID, приложение просто
  игнорирует пакеты с таким же ID.

## 6. Построчный разбор каждого файла

Ниже — файл за файлом, что делает практически каждая значимая строка или
блок кода. Внутри самих файлов тоже оставлены подробные комментарии на
русском — этот раздел README дублирует и дополнительно поясняет их.

### 6.1 `go.mod`

```
module multicast-discovery

go 1.22

require golang.org/x/net v0.35.0

require golang.org/x/sys v0.30.0 // indirect
```

- `module multicast-discovery` — имя Go-модуля (проекта). Так как проект
  не публикуется и не импортируется другими проектами, подойдёт любое
  простое имя, не обязательно доменное (`github.com/...`).
- `go 1.22` — минимальная версия Go, для которой написан код.
- `require golang.org/x/net v0.35.0` — единственная реальная внешняя
  зависимость проекта: официальный пакет `golang.org/x/net`, из которого
  используются `ipv4` и `ipv6` (см. раздел 6.10) для явного закрепления
  исходящего multicast-интерфейса.
- `require golang.org/x/sys v0.30.0 // indirect` — собственная
  зависимость самого `golang.org/x/net` (нужна ему для низкоуровневых
  системных вызовов внутри). Пометка `// indirect` означает, что наш код
  её напрямую не импортирует — это зависимость зависимости, которую Go
  подтягивает и фиксирует автоматически.
- После получения проекта нужно один раз выполнить `go mod tidy` (нужен
  интернет) — эта команда скачает обе зависимости и создаст файл
  `go.sum` с их контрольными суммами. Без `go.sum` сборка не запустится.

### 6.2 `idgen.go` — генерация ID процесса

- `func generateInstanceID() string` — единственная функция файла.
- `buf := make([]byte, 8)` — создаёт срез (slice) из 8 пустых байт, в
  которые запишется случайное значение.
- `rand.Read(buf)` — функция из пакета `crypto/rand` (криптографически
  стойкий генератор случайных чисел, а не "простой" `math/rand`)
  заполняет `buf` случайными байтами.
- Блок `if _, err := rand.Read(buf); err != nil { ... }` — если генератор
  случайных чисел по какой-то причине не сработал (крайне маловероятно),
  возвращается запасное фиксированное значение `"fallback-instance-id"`,
  чтобы приложение не "падало" из-за этого.
- `hex.EncodeToString(buf)` — превращает 8 "сырых" байт в читаемую
  16-символьную строку в шестнадцатеричном виде (например,
  `7b6d3d8363f4c0c4`) — именно эта строка и рассылается как ID копии.

### 6.3 `flags.go` — параметры командной строки

- `type Config struct { ... }` — структура, в которой хранятся все
  параметры запуска уже в удобном для остального кода виде (не строки
  командной строки, а готовые значения: адрес, число, длительность,
  булево значение "это IPv6 или нет").
- `func parseFlags() (*Config, error)` — главная функция файла.
- `flag.String("group", "", "...")` — регистрирует флаг `-group`,
  значение по умолчанию — пустая строка (значит "не задан").
  Аналогично `flag.Int` для `-port` и `flag.Duration` для `-interval` и
  `-timeout` — `flag.Duration` умеет сама разбирать строки вроде `2s`,
  `500ms`, `1m30s`.
- `flag.Parse()` — заставляет пакет `flag` прочитать реальные аргументы,
  с которыми был запущен процесс (`os.Args`), и заполнить переменные выше
  их значениями.
- `if *group == "" { return nil, errors.New(...) }` — проверка, что
  обязательный параметр `-group` действительно был передан (звёздочка
  `*group` — разыменование указателя, т.е. "значение, на которое
  указывает `group`").
- `ip := net.ParseIP(*group)` — пытается разобрать переданную строку как
  IP-адрес (подходит и для IPv4, и для IPv6 — тип `net.IP` в Go общий для
  обоих). Если строка не является корректным IP-адресом, `ParseIP`
  вернёт `nil`.
- `if !ip.IsMulticast() { ... }` — метод `IsMulticast()` у `net.IP`
  проверяет, попадает ли адрес в диапазон multicast-адресов (для IPv4 и
  IPv6 диапазоны разные, но метод сам знает оба). Если это не
  multicast-адрес (например, обычный `8.8.8.8`) — возвращается ошибка с
  понятным объяснением.
- `isIPv6 := ip.To4() == nil` — **это и есть автоматическое определение
  протокола**, о котором говорится в задании. Метод `To4()` пытается
  представить IP-адрес как классический 4-байтовый IPv4-адрес. Если это
  невозможно (адрес "чисто" IPv6, например `ff02::1234`) — `To4()`
  возвращает `nil`, и тогда `isIPv6` становится `true`.
- `if *timeout <= *interval { ... }` — здравая проверка: если время
  "устаревания" копии меньше или равно интервалу отправки анонсов,
  живые копии будут постоянно ошибочно считаться пропавшими (не успеет
  прийти следующий анонс). Приложение сразу сообщает об этой ошибке
  конфигурации, а не "странно работает" молча.
- В конце функция собирает и возвращает заполненную структуру `*Config`.

### 6.4 `netutil.go` — сетевые вспомогательные функции

- `func networkKind(isIPv6 bool) string` — простая функция-переключатель:
  возвращает строку `"udp6"`, если `isIPv6 == true`, иначе `"udp4"`.
  Именно такие строки ожидают функции стандартного пакета `net`
  (`ResolveUDPAddr`, `ListenMulticastUDP`, `DialUDP`) для указания, какой
  версией протокола пользоваться.
- `func resolveInterface(name string, isIPv6 bool) (*net.Interface,
  error)` — находит сетевой интерфейс (например, `eth0` или `Wi-Fi`) для
  приёма multicast-трафика группы того протокола, который определён в
  `isIPv6`.
    - `ifaces, err := net.Interfaces()` — сначала в любом случае получаем
      список **всех** сетевых интерфейсов машины (физических, Wi-Fi,
      виртуальных, loopback) — он нужен и для автовыбора, и для того, чтобы
      подсказать пользователю подходящие варианты в тексте ошибки.
    - `if name != "" { ... }` — если пользователь явно передал имя через
      `-iface`, ищем интерфейс с таким именем в списке и **дополнительно
      проверяем** его пригодность (см. ниже), вместо того чтобы просто
      доверять пользователю и отдавать интерфейс "как есть".
    - Если имя не передано — перебираем весь список и пропускаем
      неподходящие интерфейсы:
        - `iface.Flags&net.FlagUp == 0` — интерфейс выключен ("опущен"),
          пропускаем.
        - `iface.Flags&net.FlagMulticast == 0` — интерфейс не поддерживает
          multicast вообще, пропускаем.
        - `iface.Flags&net.FlagLoopback != 0` — это внутренний loopback
          (`127.0.0.1` / `::1`), для обмена с **другими** машинами в сети он
          не подходит, пропускаем и его.
        - `!hasAddressFamily(&iface, isIPv6)` — **важная проверка**: у
          интерфейса должен быть хотя бы один адрес нужной версии протокола
          (IPv4 или IPv6). Без неё можно было бы выбрать интерфейс, который
          формально "включён" и "умеет multicast", но не имеет, например,
          IPv4-адреса вообще (частый случай для виртуальных адаптеров VPN,
          Docker/WSL, VirtualBox, Hyper-V, Bluetooth-сети и т.п.) — тогда
          попытка присоединиться к IPv4 multicast-группе на нём заканчивается
          ошибкой операционной системы `no such network interface`, которая
          сама по себе ничего не объясняет пользователю.
    - Первый интерфейс, прошедший все проверки, возвращается как
      подходящий. Если такого не нашлось (или явно указанный интерфейс не
      прошёл проверку) — возвращается ошибка, в которую с помощью
      `describeInterfaces` подставлен список реально существующих
      multicast-интерфейсов машины, чтобы сразу было понятно, что написать
      в `-iface`.
- `func hasAddressFamily(iface *net.Interface, isIPv6 bool) bool` —
  вызывает `iface.Addrs()` (список адресов конкретного интерфейса,
  отдельно от `net.Interfaces()`, который даёт только сами интерфейсы
  без адресов) и проверяет, есть ли среди них хотя бы один адрес нужной
  версии протокола. Используется та же логика, что и в `flags.go`:
  `ipNet.IP.To4() != nil` означает "это IPv4-адрес".
- `func familyLabel(isIPv6 bool) string` — вспомогательная функция
  только для текста ошибок: превращает `true`/`false` в строку
  `"IPv6"`/`"IPv4"`.
- `func describeInterfaces(ifaces []net.Interface, isIPv6 bool) string`
  — строит короткую строку вида `eth0 [подходит], tun0` для текста
  ошибки, чтобы пользователю не пришлось отдельно запускать
  `ipconfig`/`ifconfig`/`ip link`, чтобы понять, какие интерфейсы вообще
  есть на машине и какой из них годится.

### 6.5 `tracker.go` — хранилище живых копий

- `type peerInfo struct { addr string; lastSeen time.Time }` — маленькая
  структура "запись об одной копии": её IP-адрес и время последнего
  полученного от неё сообщения.
- `type PeerTracker struct { mu sync.Mutex; peers map[string]peerInfo }`
  — основное хранилище:
    - `peers` — словарь (map) вида `instance ID → peerInfo`. Ключ — именно
      ID процесса (см. `idgen.go`), а не IP-адрес, потому что на одном
      IP-адресе может работать сразу несколько отдельных процессов
      приложения.
    - `mu sync.Mutex` — "мьютекс", механизм защиты от одновременного
      доступа. Он нужен, потому что к `peers` могут одновременно
      обращаться разные горутины (например, горутина приёма сообщений и
      горутина очистки устаревших записей), а обычный `map` в Go не
      является потокобезопасным сам по себе — без мьютекса возможна авария
      (`panic: concurrent map writes`).
- `func newPeerTracker() *PeerTracker` — "конструктор": создаёт трекер с
  уже инициализированным пустым словарём (`make(map[string]peerInfo)`).
  Без `make` карта была бы равна `nil`, и запись в неё привела бы к
  панике.
- `func (t *PeerTracker) Touch(id, addr string) bool`:
    - `t.mu.Lock()` / `defer t.mu.Unlock()` — захватывает мьютекс на время
      выполнения метода, чтобы никакая другая горутина не могла в этот
      момент читать или менять `peers`; `defer` гарантирует, что
      разблокировка произойдёт при выходе из функции в любом случае.
    - `_, existed := t.peers[id]` — проверяет, была ли эта копия уже
      известна **до** этого вызова.
    - `t.peers[id] = peerInfo{addr: addr, lastSeen: time.Now()}` —
      записывает (или обновляет) информацию об этой копии: адрес и текущее
      время.
    - `return !existed` — возвращает `true`, только если копия оказалась
      **новой**. Это значение используется в `listener.go`, чтобы понять,
      нужно ли заново печатать список (печатать на каждое отдельное
      сообщение не нужно — только когда список реально изменился).
- `func (t *PeerTracker) RemoveExpired(timeout time.Duration) bool`:
    - Тоже сначала блокирует мьютекс.
    - `changed := false` — флаг, изменился ли список за этот вызов.
    - `for id, info := range t.peers { ... }` — перебирает все известные
      копии.
    - `if now.Sub(info.lastSeen) > timeout { delete(t.peers, id); changed
    = true }` — если с момента последнего анонса прошло больше, чем
      `timeout`, копия считается пропавшей и удаляется из словаря
      (`delete`).
    - Возвращает `changed` — было ли удалено хоть что-то.
- `func (t *PeerTracker) Snapshot() []string`:
    - Возвращает список IP-адресов всех **сейчас** известных живых копий.
    - `sort.Strings(addrs)` — сортирует список по алфавиту/числовому виду
      строки. Это сделано специально: порядок перебора элементов `map` в Go
      не гарантирован (может меняться от вызова к вызову), и без
      сортировки список в консоли "прыгал" бы местами без всякой причины
      при каждом выводе.

### 6.6 `listener.go` — приём сообщений

- `func startListener(cfg *Config, selfID string, iface *net.Interface,
  tracker *PeerTracker) error`:
    - Интерфейс (`iface`) сюда теперь **передаётся снаружи**, из
      `main.go`, а не вычисляется заново внутри этой функции. Раньше
      `listener.go` сам вызывал `resolveInterface`, а `sender.go` при
      отправке полагался на выбор ОС по умолчанию — в результате на
      машинах с несколькими сетевыми адаптерами (типично для macOS: Wi-Fi,
      Ethernet, VPN/utun и т.д.) приёмник и отправитель могли фактически
      работать на разных интерфейсах и просто не видеть анонсы друг друга,
      хотя оба стартовали без единой ошибки. Теперь интерфейс определяется
      один раз в `main.go` и передаётся в обе функции — они гарантированно
      согласованы.
    - `network := networkKind(cfg.IsIPv6)` — получает `"udp4"` или
      `"udp6"`.
    - `net.JoinHostPort(cfg.Group, strconv.Itoa(cfg.Port))` — аккуратно
      "склеивает" адрес группы и порт в одну строку. Для IPv4 получится
      `"224.1.1.1:9999"`, а для IPv6 — `"[ff02::1234]:9999"` (обратите
      внимание на квадратные скобки: без них строка с несколькими
      двоеточиями внутри IPv6-адреса была бы неоднозначной — непонятно, где
      заканчивается адрес и начинается порт).
    - `net.ResolveUDPAddr(network, ...)` — превращает эту строку в
      структуру `*net.UDPAddr`, с которой уже работают низкоуровневые
      сетевые функции.
    - `net.ListenMulticastUDP(network, iface, groupAddr)` — ключевая
      строка всего файла. Эта функция стандартной библиотеки одновременно:
        1. создаёт UDP-сокет;
        2. присоединяет его к указанной multicast-группе на указанном
           интерфейсе (технически это соответствует системному вызову
           `setsockopt` с опцией `IP_ADD_MEMBERSHIP` для IPv4 или
           `IPV6_JOIN_GROUP` для IPv6);
        3. после этого сокет начинает получать **все** UDP-пакеты, которые
           кто угодно в сети отправляет на этот адрес группы и порт — а не
           только пакеты, адресованные лично нам.
    - `go receiveLoop(conn, selfID, tracker)` — ключевое слово `go` перед
      вызовом функции запускает её в **отдельной горутине** — лёгком
      потоке выполнения, который работает параллельно остальному коду.
      Именно поэтому приём сообщений не "морозит" остальную программу.
    - `log.Printf(...)` — печатает в консоль (с меткой времени), что
      прослушивание успешно началось.
- `func receiveLoop(conn *net.UDPConn, selfID string, tracker
  *PeerTracker)` — тело этой самой горутины, бесконечный цикл `for { ...
  }`:
    - `n, srcAddr, err := conn.ReadFromUDP(buf)` — блокирующий вызов:
      горутина "засыпает" здесь и ждёт, пока не придёт очередной UDP-пакет.
      `n` — сколько байт реально пришло, `srcAddr` — с какого IP-адреса и
      порта пришёл пакет.
    - `if err != nil { ...; return }` — если чтение завершилось с ошибкой
      (это происходит, когда сокет закрывается при остановке приложения),
      горутина печатает сообщение и аккуратно завершается — вместо того,
      чтобы бесконечно пытаться читать из уже закрытого сокета.
    - `receivedID := string(buf[:n])` — превращает полученные `n` байт в
      строку — это и есть ID отправившей копии (см. раздел 5 про формат
      сообщений).
    - `if receivedID == selfID { continue }` — если пришло **наше же**
      сообщение (из-за multicast loopback), просто игнорируем его и ждём
      следующий пакет (`continue` переходит к следующей итерации цикла).
    - `peerIP := srcAddr.IP.String()` — превращает IP-адрес отправителя в
      обычную читаемую строку (`"192.168.1.5"` или `"fe80::1"`).
    - `if tracker.Touch(receivedID, peerIP) { printPeers(...) }` —
      регистрирует получение анонса в трекере; если эта копия оказалась
      новой (`Touch` вернул `true`), сразу же печатается обновлённый
      список живых копий.

### 6.7 `sender.go` — отправка анонсов

- `func startSender(cfg *Config, selfID string, iface *net.Interface,
  stop <-chan struct{}) error`:
    - Как и в `listener.go`, `iface` передаётся из `main.go`, а не
      выбирается заново — см. объяснение выше.
    - Так же, как в `listener.go`, собирает адрес группы через
      `net.JoinHostPort` и `net.ResolveUDPAddr`.
    - **`if cfg.IsIPv6 && groupAddr.IP.IsLinkLocalMulticast() { groupAddr.Zone
    = iface.Name }`** — это самый важный блок всего файла, и вот почему.
      Link-local IPv6-адреса (диапазон `ff02::/16`, которым принадлежит,
      например, `ff02::1234` — самый обычный выбор для локальной сети) не
      являются глобально маршрутизируемыми: у **каждого** сетевого
      интерфейса машины свой собственный "срез" (zone) этого адресного
      пространства (см. [RFC 4007](https://www.rfc-editor.org/rfc/rfc4007)).
      Без явно указанной зоны операционная система физически не может
      решить, через какой интерфейс отправлять пакет, и вызов `connect()`
      внутри `DialUDP` падает с ошибкой **`no route to host`** — причём это
      происходит *до* того, как успевает сработать `setMulticastInterface`
      ниже: та функция настраивает уже открытый сокет, а на этом шаге
      сокета ещё не существует. Метод `IsLinkLocalMulticast()` у `net.IP`
      определяет, действительно ли адрес относится к этому диапазону (для
      не-link-local, "глобальных" IPv6 multicast-адресов зона не нужна и не
      проставляется). Поле `Zone` у `net.UDPAddr` — это и есть тот самый
      "срез": если вывести такой адрес в лог, будет видно `%` с именем
      интерфейса, например `[ff02::1234%eth0]:9999`.
    - `net.DialUDP(network, nil, groupAddr)` — создаёт UDP-соединение,
      "нацеленное" на адрес группы. `nil` вместо локального адреса означает
      "пусть операционная система сама выберет свободный локальный порт".
      Сам по себе `DialUDP` **не определяет**, через какой сетевой
      интерфейс уйдут multicast-пакеты, — это отдельная настройка сокета
      (следующий пункт).
    - `setMulticastInterface(conn, iface, cfg.IsIPv6)` — явно закрепляет за
      уже созданным сокетом тот же сетевой интерфейс, на котором
      `startListener` слушает группу (реализация — см. раздел 6.10). Если
      закрепить интерфейс не удалось — приложение не падает, а печатает
      предупреждение и продолжает работать с интерфейсом по умолчанию,
      который выберет ОС.
    - `go sendLoop(conn, selfID, cfg.SendInterval, stop)` — запускает цикл
      отправки анонсов в отдельной горутине, как и приём сообщений.
- `func sendLoop(conn *net.UDPConn, selfID string, interval
  time.Duration, stop <-chan struct{})`:
    - `ticker := time.NewTicker(interval)` — создаёт "тикер": объект,
      который каждые `interval` (например, каждые 2 секунды) присылает
      сигнал в канал `ticker.C`.
    - `defer ticker.Stop()` / `defer conn.Close()` — гарантируют, что при
      выходе из функции тикер будет остановлен, а сетевое соединение
      закрыто (освобождены системные ресурсы), даже если выход произойдёт
      через `return` в середине функции.
    - `sendAnnounce(conn, selfID)` (до цикла) — отправляет первый анонс
      сразу при запуске, не дожидаясь первого срабатывания тикера, чтобы
      другие копии узнали о нашем появлении как можно быстрее.
    - `for { select { case <-ticker.C: ...; case <-stop: return } }` —
      основной цикл. Конструкция `select` одновременно "слушает" два
      канала:
        - когда срабатывает `ticker.C` (пришло время очередной отправки) —
          вызывается `sendAnnounce`;
        - когда закрывается канал `stop` (сигнал остановки всего
          приложения, см. `main.go`) — функция завершает работу через
          `return`, что запускает отложенные `defer`-вызовы выше (закрытие
          соединения).
- `func sendAnnounce(conn *net.UDPConn, selfID string)`:
    - `conn.Write([]byte(selfID))` — отправляет в сеть один UDP-пакет,
      содержащий байты instance ID. Так как `conn` был создан через
      `DialUDP` с уже "зафиксированным" адресом группы, `Write` (а не
      `WriteTo`) сам знает, куда слать пакет.
    - Если отправка не удалась — ошибка просто логируется, не прерывая
      работу приложения (следующая попытка будет через `interval`).

### 6.8 `printer.go` — вывод списка

- `func printPeers(tracker *PeerTracker, reason string)`:
    - `addrs := tracker.Snapshot()` — получает актуальный отсортированный
      список IP-адресов живых копий.
    - `log.Println(reason)` — печатает (с меткой времени) короткую причину
      изменения: "обнаружена новая копия..." или "...копии исчезли...".
    - `if len(addrs) == 0 { ...; return }` — если список пуст (например,
      вообще не осталось других копий в сети), печатается отдельное
      сообщение об этом, и функция завершается — незачем печатать пустой
      список ниже.
    - Иначе — печатается заголовок "текущий список живых копий приложения"
      и построчно (`for _, addr := range addrs { fmt.Printf(...) }`)
      каждый IP-адрес с отступом и маркером `-`.

### 6.9 `main.go` — точка входа

- `func main()`:
    - `cfg, err := parseFlags()` — разбор параметров командной строки (см.
      `flags.go`). Если ошибка — `log.Fatalf` печатает её и **сразу
      завершает процесс** (Fatal-функции внутри себя вызывают `os.Exit(1)`).
    - `selfID := generateInstanceID()` — генерирует уникальный ID этого
      процесса один раз при старте (см. `idgen.go`).
    - Блок `protoName := "IPv4"; if cfg.IsIPv6 { protoName = "IPv6" }` —
      просто для красивого информационного сообщения в лог о том, какой
      протокол используется и почему (см. `log.Printf` ниже).
    - `tracker := newPeerTracker()` — создаёт пустое хранилище живых
      копий.
    - `iface, err := resolveInterface(cfg.Iface, cfg.IsIPv6)` — определяет
      сетевой интерфейс **один раз**, до запуска и приёма, и отправки. Это
      важное отличие от более ранней версии, где `listener.go` и
      `sender.go` каждый выбирал интерфейс самостоятельно (а `sender.go`
      вообще полагался на маршрут ОС по умолчанию) — см. подробности в
      разделах 6.6–6.7 и в разделе 7.1 про типичную проблему на macOS.
      Если подходящего интерфейса нет — `log.Fatalf` сразу завершает
      приложение с понятным сообщением и списком доступных интерфейсов
      (см. `netutil.go`).
    - `stop := make(chan struct{})` — создаёт **канал без данных**
      (`struct{}` — "пустой" тип, который ничего не весит; такой канал
      используется просто как "флаг остановки"). Как только этот канал
      будет закрыт (`close(stop)`), **все** горутины, которые его слушают
      через `select { case <-stop: ... }`, узнают об этом одновременно —
      это стандартный в Go способ разослать сигнал сразу многим
      получателям.
    - `startListener(cfg, selfID, iface, tracker)` — запускает приём
      multicast-сообщений (см. `listener.go`) на уже определённом
      интерфейсе. Если не получилось — `log.Fatalf` завершает приложение с
      понятной ошибкой.
    - `startSender(cfg, selfID, iface, stop)` — запускает периодическую
      отправку анонсов (см. `sender.go`) через тот же самый интерфейс.
    - `go cleanupLoop(cfg, tracker, stop)` — запускает в отдельной
      горутине периодическую проверку "не устарела ли какая-то запись".
    - `sigCh := make(chan os.Signal, 1)` и `signal.Notify(sigCh,
    os.Interrupt, syscall.SIGTERM)` — подписывают приложение на сигналы
      операционной системы: `os.Interrupt` — это нажатие Ctrl+C в
      терминале, `syscall.SIGTERM` — "вежливая" команда завершения процесса
      (например, от `kill <pid>` без флагов или от системы управления
      процессами).
    - `<-sigCh` — здесь главная горутина (`main`) **блокируется** и просто
      ждёт, пока не придёт один из этих сигналов — всё это время
      приложение продолжает слушать и отправлять сообщения в фоновых
      горутинах.
    - После получения сигнала: `log.Println(...)`, `close(stop)`
      (сигнализирует всем фоновым горутинам завершиться) и `time.Sleep(200
        * time.Millisecond)` — небольшая пауза, чтобы дать горутинам время
    аккуратно закрыть свои сетевые соединения, прежде чем процесс
    завершится полностью (функция `main` возвращается, и программа
          заканчивает работу).
- `func cleanupLoop(cfg *Config, tracker *PeerTracker, stop <-chan
  struct{})`:
    - Похожа по структуре на `sendLoop` из `sender.go`: тикер, который
      срабатывает раз в `cfg.SendInterval`, и `select`, слушающий либо
      тикер, либо канал остановки.
    - `if tracker.RemoveExpired(cfg.PeerTimeout) { printPeers(...) }` —
      каждый раз при срабатывании тикера проверяет, не "устарели" ли какие-
      то записи о копиях (то есть не пропали ли они из сети), и если хотя
      бы одна запись была удалена — заново печатает обновлённый список.
      Именно эта функция отвечает за обнаружение **исчезновения** копий,
      в паре с `Touch` в `tracker.go`, отвечающим за обнаружение
      **появления**.

### 6.10 `setMulticastInterface` (в `sender.go`) — фиксация исходящего интерфейса

```go
func setMulticastInterface(conn *net.UDPConn, iface *net.Interface, isIPv6 bool) error {
	if isIPv6 {
		return ipv6.NewPacketConn(conn).SetMulticastInterface(iface)
	}
	return ipv4.NewPacketConn(conn).SetMulticastInterface(iface)
}
```

Раньше это делалось вручную через `syscall.SetsockoptInt` /
`SetsockoptInet4Addr` в отдельном файле под каждую операционную систему —
рабочий, но низкоуровневый и негибкий способ (для каждой новой ОС
понадобился бы ещё один файл с ещё одним набором системных вызовов).
Сейчас вместо этого используется официальный пакет
[`golang.org/x/net`](https://pkg.go.dev/golang.org/x/net) — он
поддерживается той же командой, что развивает сам язык Go, и как раз
создан для подобных сетевых операций, которых не хватает в стандартной
библиотеке.

- `ipv4.NewPacketConn(conn)` / `ipv6.NewPacketConn(conn)` — "оборачивают"
  уже существующее `*net.UDPConn` в объект с дополнительными методами
  управления IP-уровнем — в стандартном пакете `net` таких методов нет.
- `.SetMulticastInterface(iface)` — тот самый системный вызов
  `setsockopt` с опцией `IP_MULTICAST_IF` (для IPv4) или
  `IPV6_MULTICAST_IF` (для IPv6), но уже без единой строчки `syscall` в
  нашем коде — библиотека сама учитывает особенности конкретной
  операционной системы внутри себя.
- Один и тот же вызов работает одинаково на macOS, Linux и Windows —
  никаких файлов вида `_darwin.go` / `_windows.go` для этого больше не
  нужно.

Поскольку это внешняя зависимость (не входит в стандартную поставку Go),
она объявлена в `go.mod` (`require golang.org/x/net ...`) — из-за этого
перед первой сборкой нужно один раз выполнить `go mod tidy` (см. раздел
3), скачивающий код зависимости и фиксирующий её версию в `go.sum`.

## 7. Диагностика: копии не находят друг друга

Если приложение стартует без единой ошибки в обоих терминалах (видно
строки "слушаю multicast-группу..." и "отправляю анонсы..."), но списки
живых копий всё равно пустые — проблема не в коде приложения как
таковом, а в сети или в ОС. Два самых частых случая ниже.

### 7.1 macOS: разные интерфейсы у отправителя и получателя, либо firewall

На macOS (особенно в связке с GoLand, где часто активны VPN/iCloud
Private Relay) на одной машине обычно есть сразу несколько сетевых
интерфейсов: `en0` (Wi-Fi), `en5`/`en6` (Ethernet-адаптеры), `utun0`,
`utun1`, ... (VPN, iCloud Private Relay), `awdl0`/`llw0` (AirDrop /
Apple Wireless Direct Link), `bridge0`/`bridge100` (виртуализация) и
т.д. Раньше в этом проекте приёмник (`listener.go`) и отправитель
(`sender.go`) каждый **независимо** выбирал сетевой интерфейс — приёмник
искал первый подходящий сам, а отправитель полагался на маршрут ОС по
умолчанию. Если эти выборы не совпадали, две копии на одной сети
формально работали без ошибок, но никогда не видели анонсов друг друга.

**Это исправлено**: теперь интерфейс определяется один раз в `main.go` и
передаётся и в `startListener`, и в `startSender` — они гарантированно
работают на одном и том же интерфейсе, а исходящий multicast-интерфейс
дополнительно явно закрепляется через `golang.org/x/net` (см. разделы 6.9
и 6.10). Если вы тестировали более раннюю версию — пересоберите проект из
актуальных файлов.

Отдельная, не связанная с кодом причина — **firewall macOS**: при первом
запуске система должна была показать диалог "Do you want the application
to accept incoming network connections?". Если он был случайно закрыт
или отклонён (что легко сделать в связке с IDE), входящие
UDP-multicast-пакеты будут молча блокироваться. Проверьте System Settings
→ Network → Firewall, и на время теста попробуйте выключить его совсем,
чтобы исключить эту причину.

Если сомневаетесь, какой интерфейс "настоящий", — передайте `-iface`
одинаково в обоих терминалах явно (например, `-iface en0`) вместо того,
чтобы полагаться на автовыбор:

```bash
go run . -group 224.1.1.1 -port 6767 -iface en0
```

### 7.2 Ошибка "no such network interface"

Если при запуске вы видите ошибку вида:

```
не удалось запустить приём multicast-сообщений: не удалось присоединиться
к multicast-группе: listen udp4 224.1.1.1:6767: no such network interface
```

это значит, что приложение выбрало (автоматически или по вашему `-iface`)
сетевой интерфейс, у которого нет адреса нужной версии протокола (в
примере выше — нет IPv4-адреса). Чаще всего так происходит на машинах с
несколькими сетевыми адаптерами: VPN (WireGuard, OpenVPN, Tailscale),
виртуальные адаптеры Docker/WSL/VirtualBox/Hyper-V, Bluetooth-сеть и
подобные — они формально "включены" и умеют multicast, но реального
IPv4/IPv6-адреса на них может не быть.

Начиная с этой версии, `resolveInterface` в `netutil.go` сам проверяет
это условие (см. раздел 6.4) и при ошибке сразу печатает список реально
подходящих интерфейсов машины, например:

```
интерфейс "fake0" не найден; доступные интерфейсы: eth0 [подходит], wlan0 [подходит]
```

Что делать:

1. Посмотрите на список подходящих интерфейсов в тексте ошибки (пометка
   `[подходит]`) и передайте один из них через `-iface`:
   ```bash
   ./mcdisc -group 224.1.1.1 -port 6767 -iface eth0
   ```
2. Если списка нет вообще или в нём нет ни одного `[подходит]` —
   проверьте, что на нужном сетевом адаптере действительно включён и
   настроен IPv4 (или IPv6, если группа IPv6) — например, командой
   `ifconfig`.

### 7.3 Ошибка "no route to host" на IPv6

Если при запуске с IPv6-группой вы видите что-то вроде:

```
слушаю multicast-группу [ff02::1234]:9999 на интерфейсе en0
отправляю анонсы присутствия в группу ...
не удалось запустить отправку multicast-сообщений: не удалось открыть
сокет для отправки анонсов: dial udp6 [ff02::1234]:9999: connect: no
route to host
```

— обратите внимание: `listener.go` (приём) уже успешно присоединился к
группе, а вот `sender.go` (отправка) падает. Причина — в самой природе
IPv6-адресов, а не в конкретном интерфейсе.

Адреса вида `ff02::...` — это **link-local** multicast (см.
[RFC 4007](https://www.rfc-editor.org/rfc/rfc4007)): такой адрес не
существует "глобально" на всю машину, у каждого сетевого интерфейса свой
собственный срез (zone) этого адресного пространства. `ListenMulticastUDP`
в `listener.go` получает интерфейс отдельным параметром, поэтому знает,
какую зону использовать. А `DialUDP` в `sender.go` до этого фикса
получал только "голый" адрес без зоны — и операционная система просто не
могла понять, через какой интерфейс идти, отвечая `no route to host`.

**Это исправлено**: теперь перед вызовом `DialUDP` для link-local
IPv6-адресов приложение само проставляет зону — тот же интерфейс, что
использует `listener.go` (см. раздел 6.7, блок с `IsLinkLocalMulticast()`
/ `groupAddr.Zone`). Если вы тестировали более раннюю версию —
пересоберите проект из актуальных файлов, и ошибка должна исчезнуть.

Если ошибка всё равно повторяется — почти наверняка это значит, что на
выбранном интерфейсе вообще нет активного IPv6-соединения в локальной
сети (например, роутер/Wi-Fi точка доступа не раздаёт IPv6 или интерфейс
физически не подключён). Проверьте это командой `ifconfig <интерфейс>` —
у интерфейса должен быть адрес вида `fe80::...`.

## 8. Известные ограничения

- **TTL / область действия multicast.** IPv4-пакеты по умолчанию
  отправляются с TTL, который может ограничить их распространение одним
  сегментом сети (не будут проходить через маршрутизаторы без специальной
  настройки multicast-маршрутизации). Для обнаружения "в локальной сети",
  как и требуется в задаче, этого достаточно.
- **Multicast через настоящий Wi-Fi-роутер часто просто не работает — и
  это не баг приложения.** Многие домашние/офисные роутеры и точки
  доступа либо не форвардят IPv6 multicast между Wi-Fi и проводным
  сегментом вовсе, либо требуют включённого MLD snooping/proxying,
  который часто отключён или работает криво в прошивке "из коробки". Для
  IPv4 похожая проблема называется IGMP snooping. Если два устройства на
  одном компьютере (или в одном L2-сегменте через прямой кабель/один и
  тот же Wi-Fi SSID без клиентской изоляции) видят друг друга, а через
  реальный роутер — нет, дело почти наверняка в настройках самого
  роутера, а не в этом коде. Проверить это средствами приложения
  невозможно — это внешняя сетевая инфраструктура.
- **Межсетевые экраны (firewall).** Если копии не находят друг друга на
  разных машинах, в первую очередь проверьте, не блокирует ли брандмауэр
  входящий UDP-трафик на выбранный порт (по умолчанию `9999`).
- **Формат сообщения не аутентифицирован.** Любой, кто отправит в эту же
  multicast-группу и порт UDP-пакет, будет воспринят как "живая копия"
  (если только его "ID" случайно не совпадёт с собственным ID
  какого-либо процесса). Для учебной задачи обнаружения присутствия в
  доверенной локальной сети это осознанное упрощение.

## 9. Как остановить приложение

Нажмите `Ctrl+C` в терминале, где оно запущено, либо отправьте процессу
сигнал `SIGTERM` (например, командой `kill <PID>` без дополнительных
флагов). Приложение перехватит сигнал, аккуратно закроет сетевые
соединения и завершится (подробности — в разделе 6.9, разбор `main.go`).
